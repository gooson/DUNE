# Life 탭 독립 설계 검토와 실행 계획 · Astra

## Context

라이프 탭을 다른 세 탭의 최신 디자인과 맞추면서 습관 분류·순서·입력·시각화를 개선하기 위한 독립 조사다. 이 문서는 **제안**이며 앱 구현·시뮬레이터 캡처·검증 완료 기록이 아니다. 현재 workspace의 소스와 저장소 설계 문서를 읽었다. 사용자 인터뷰나 실제 손가락 오조작 재현을 수행하지 않았으므로 사용성 문제의 빈도를 확정하지 않는다.

핵심 판단은 “분류를 많이 보여주기”보다 **오늘 할 일을 찾고 안전하게 기록하는 속도**를 높이는 것이다. 기존 오늘/주간/다가오는 일정 분리는 정확한 기반이므로 유지한다. 시각화의 강조는 집계가 뒷받침하는 범위까지만 한다.

## Requirements

### 분류 축을 명시적으로 분리

| 축 | 질문 | 화면에서의 역할 |
|---|---|---|
| 행동 영역 | 무엇에 관한 습관인가? | 아이콘/보조 필터. 현재 12개 원시값 유지 |
| 기록 방식 | 어떻게 입력하는가? | 완료 체크·횟수·시간에 맞춘 컨트롤 |
| 일정 | 언제 대상인가? | 오늘 / 이번 주 목표 / 다가오는 일정의 주 분류 |
| 선호 시간대 | 하루 중 언제 하는가? | 행의 낮은 메타데이터, 필요한 경우 그룹 |
| 데이터 출처 | 직접 입력인가, 연동인가? | 자동 확인 표식, 수정 가능 여부, 출처 |
| 진행 상태 | 지금 무엇을 할 수 있는가? | 미완료/부분 기록/완료/예정/미룸/건너뜀 표현 |

“건강·체크·자동·아침”을 같은 수준의 카테고리로 섞지 않는다. 템플릿의 건강/운동/생산성/마음챙김/생활은 **찾기 위한 묶음**이며 저장된 아이콘 분류와 동일 필드처럼 제시하지 않는다. 첫 버전에서 카테고리 통합을 위해 CloudKit raw value를 바꾸지 않는다. 새 행동 분류가 필요하면 별도 매핑을 정의하되 기존 데이터 의미를 소급 변경하지 않는다.

### 권장 정보 순서

1. **HABITS 히어로**: 오늘 완료 `2/5`와 “오늘 3개 남음”, 104pt 링. 오늘 대상이 없으면 “오늘 예정 없음”, 습관 자체가 없으면 시작 안내. 주간·자동을 오늘 분모에 더하지 않는다. 완료/대상/남음 세 요약은 제거하고 짧은 안내 한 번으로 압축한다.
2. **오늘**: 미완료와 부분 기록이 먼저. 기한 지난 반복 습관에는 실제 예정일을 표시한다. 시간대는 보조 정보로 사용하고 소량 목록에서 네 개 헤더를 만들지 않는다.
3. **오늘 완료**: 처음에는 요약+펼침. 완료 직후 행을 즉시 사라지게 하거나 손가락 밑을 재정렬하지 않는다. 체크/횟수/시간은 실행 취소를 제공하고 VoiceOver 포커스도 보존한다. interval은 재탭이 취소가 아닌 현재 계약을 구분해야 한다.
4. **이번 주 목표**: `이번 주 2/3일`과 `오늘 10/30분`을 분리한다. 오늘 기록 버튼은 유지하되 날짜를 지정하지 않은 주간 목표를 “오늘 남은 일”로 승격하지 않는다. 요일을 새로 추정하지 않는다.
5. **다가오는 일정**: 가까운 실제 예정일 순. 첫 완료 대기·미래 시작은 날짜 있음/없음을 구분. 조기 완료 접근을 유지한다.
6. **자동으로 확인한 운동**: 출처와 실제 기간이 있는 간결한 요약. 기본 운동 규칙은 펼쳐서 전체 확인. 사용자 연동 목표는 오늘/주간 등 실제 의미를 별도로 표시한다.
7. **기록 흐름**: 일별 완료 개수와 기록 달력, 필요하면 주간 보고서 진입. 현재 데이터 한계가 있는 완료율을 거대한 성과 지표로 만들지 않는다.
8. **습관 관리**: 활성/보관 목록·순서·이력 경로를 명확히 유지. 추가는 기존 상단 + 경로를 보존한다.

Hero를 “다음 할 일” 추천 엔진으로 확장하지 않는다. 현재 데이터에는 중요도나 마감 시각이 없으며 시간대만으로 “지금 해야 함”을 단정할 수 없다. 우선순위 기본값은 기한 지난 반복→오늘 미완료이며, 같은 그룹 안에서는 기존 `sortOrder`를 유지한다. 정렬 계약을 바꾸는 경우 수동 순서와 충돌을 문서화한다. 현재 시간마다 목록을 자동 재배열하지 않는다.

넓은 화면에서도 오늘 행동이 왼쪽 주 영역을 차지하도록 한다. 오른쪽에는 이번 주/다가오는 일정 같은 보조 계획을 배치할 수 있지만 자동 성취의 긴 목록이 오늘 할 일과 동등한 첫 영역을 점유하지 않게 한다. 접근성 크기는 읽기 순서의 한 열로 전환한다.

### 조작 계약

| 종류 | 핵심 표현 | 주 동작 | 보완 |
|---|---|---|---|
| 체크 | 이름, 일정, 완료 상태 | 명시적인 넓은 완료 버튼 | 체크 영역을 넓게 하되 더보기와 형제 영역으로 분리, 중복 토글 방지 |
| 횟수 | `물 3/8잔`, 낮은 진행 막대 | `+1잔` 최소44pt, 별도 감소 | 숫자와 단위를 함께 읽기, 0 이하 감소 불가, 목표 초과 기록은 실제값 보존 |
| 시간 | `독서 오늘 10/30분` | `시간 기록` 최소44pt | 합계 수정인지 추가 기록인지 동사로 명시. 기존 교체 저장을 `+10분`처럼 표현 금지 |
| 반복 | 실제 예정일·주기·상태 | 완료 또는 미리 완료 | 미룸/건너뜀/이력은 더보기에서 유지. “아직 아님”과 실행 불가를 혼동하지 않음 |
| 자동 연동 | 출처·기간·실제 확인값 | 출처/이력 확인 | 수동 완료 버튼을 만들지 않음. 조회 실패/기록 없음/권한을 구분할 수 있는 경우만 해당 상태 표시 |

최소44pt는 새 컴포넌트 설계 기준이며 현재 앱 전체 충족을 검증했다는 뜻이 아니다. 기본 행 높이를 크게 고정하기보다 버튼 영역을 확보하고 긴 이름·큰 글씨에서 컨트롤을 다음 줄로 내려 자연 확장한다. 핵심 동작에 사용자 언어의 accessibility label/value를 제공한다. 아이콘 색만으로 상태를 구분하지 않는다.

시간·횟수 편집은 **입력 검증 성공 후 저장값을 변경**한다. 현재 `LifeView.updateValue`는 오늘 로그를 삭제한 다음 `createValidatedLog`를 호출하며, 이 메서드는 duration 1440 또는 count 999 초과를 거절한다. 따라서 예컨대 기존30분에서1500분을 입력하면 새 로그 생성이 실패한 뒤 기존 로그만 삭제될 수 있다. 새 UI 구현 전에 이 순서를 고치고 오류는 해당 입력 가까이 표시해야 한다. 이 문서는 소스 경로로 위험을 확인했으며 런타임 재현 테스트는 수행하지 않았다.

기록 변경과 동시에 Hero/행/오늘 완료/이력이 일관되게 갱신되어야 한다. 기존 `LifeHabitLogSync`와 Query 격리는 유지한다. 저장 실패 시 화면에 성공한 것처럼 남기는 동작을 금지한다.

### 습관 생성/편집 의미

현재 폼의 “Icon” 선택은 실제 행동 카테고리 필터까지 결정한다. 사용자에게 의미를 드러내도록 “분류와 아이콘”처럼 표현하고 선택 결과를 미리 보여준다. 입력 순서는 이름→행동 분류→기록 방식/목표→일정→선호 시간/알림→연동으로 제안한다. 빈도와 목표를 읽은 뒤 아래처럼 한 문장 요약을 제공한다.

- 매일 + 시간: “매일30분 기록하면 완료”.
- 주3일 + 시간: “하루30분을 채운 날을 주3일 목표로 계산”.
- 30일 반복 + 체크: “완료 기준으로 다음 일정을 계산” 등 실제 cycle 계산 규칙에 맞는 설명. 정확한 anchor/skip/snooze 계약을 확인한 뒤 문구 확정.

duration의 자유 단위 라벨은 시간 계산과 의미가 달라질 수 있으므로 분 단위를 고정하고 기존 custom label의 처리 정책을 별도로 정한다. count의 소수·수량 단위와 `+1` 의미도 확인한다. interval은 현재 타입이 duration/count여도 `isCycleBased`가 입력 UI를 체크로 바꾸므로, 폼에서 허용하는 조합과 실제 기록 컨트롤을 일치시키는 결정이 필요하다. 이미 저장된 조합은 자동 삭제/변환하지 않는다.

## 시각화의 정확성 검토

### 현재 집계의 한계

근거는 `DUNE/Domain/UseCases/HabitAnalyticsService.swift`와 `LifeView.recalculateAnalytics`다.

1. `HabitSnapshot`에는 생성일, 보관일, 목표 변경 이력, 실제 주기 예정일이 없다. 현재 활성 습관/현재 목표를 과거 주·월에도 적용한다. 새 습관을 추가하거나 보관·목표 수정하면 과거 “완료율”이 달라질 수 있다.
2. `weeklyGoalCount`는 interval에 `max(1, 7 / interval)`을 사용한다. 90일 주기도 매주 최소1개 목표로 계산하므로 실제 예정이 없는 주를 미달처럼 표현할 수 있다.
3. 이번 주 rate는 full-week 목표를 분모로 사용한다. 진행 중인 수요일과 지난주 전체를 동일한 성과 비교처럼 해석하면 불공정하다. 월간 weekly 목표도 `daysInMonth / 7`로 환산되어 실제 경계 주 수와 다르다.
4. Hero 추세는 수동 습관, 생성일 이후, 현재 시각 이전, auto 완료 제외를 별도로 처리한다. 하단 analytics는 모든 활성 습관 snapshot을 전달하므로 Hero와 같은 모집단이라고 보장할 수 없다.
5. 기본 자동 운동은 월–일 경계를 쓰고 수동 analytics는 `Calendar.current` 주 경계를 쓴다. 같은 화면에 놓을 때 기간 라벨을 생략하면 같은 주라고 오인할 수 있다.
6. `bestHabits`/`worstHabits`는 동일 모집단의 앞/뒤3개다. 습관 수가 적거나 동률이면 같은 습관이 양쪽에 등장할 수 있고, 진행 중 주의 “개선 필요”도 실제 일정 근거가 부족하다.

### 권장 데이터 계약

첫 개편에서 과거 목표 이력을 복원하는 척하지 않는다. 루트 시각화는 **현재 수동 습관의 일별 완료 기록 수**를 사용하고 이 범위를 설명한다. 하루 여러 로그는 목표 충족 날짜로 합쳐 한 습관당 하루 한 번으로 세는 기존 `HabitStreakService.completedDates` 계약을 유지한다. skip/snooze는 완료가 아니다.

일별 막대는 오늘 링과 의미가 다르다. 링은 오늘 대상 일정의 현재 상태이고, 막대는 해당 날짜의 기록 수이며 주간/조기 완료가 들어갈 수 있다. 시안에서 두 수치를 무조건 같게 만들거나 같은 denominator를 붙이지 않는다. 새 습관 생성 전은 관측 대상 없음, 생성 후 무기록일은 완료0개로 구분한다. 활성 습관만 대상으로 집계하면 보관으로 과거 개수가 바뀔 수 있음을 설명하고, 진정한 역사 기록 보존은 별도 범위에서 설계한다.

완료율·보고서를 유지할 경우 `현재 목표 기준`과 `진행 중`을 명확히 표시하고, interval 포함 집계가 실제 스케줄과 맞도록 고치기 전에는 개선율/낙제 순위를 강조하지 않는다. 단순 라벨 변경만으로 부정확한 예정 분모를 정당화할 수 없다. 정확한 과거 완료율을 제품 목표로 삼는 경우에는 생성/보관/목표 변경/주기 이력 스냅샷이 필요한 별도 데이터 설계다. 이번 디자인 개편에 스키마 변경을 숨겨 넣지 않는다.

자동 운동 5회와7회는 하나의 원천 진행에 단계형 표시를 고려할 수 있다. 단, 9개 규칙을3개 카드로 압축해도 “3/3 완료”로 기존 합계를 임의 환산하지 않는다. 부위별 성취와 운동 횟수 역시 서로 더하지 않는다. 요약은 “이번 주 운동4회·달리기8.2km”처럼 실제 단위와 기간을 보존하고 상세에서 기존 규칙을 확인한다. 없는 값은 가짜0이나 완료로 채우지 않는다.

## 통합 시 유지할 독립 판단

1. 주간 목표는 오늘의 할 일과 같은 리스트/분모로 합치지 않는다. 다만 사용자에게 **오늘 기록할 수 있는 주간 목표**라는 접근은 제공한다.
2. 카테고리의 개수보다 일정·입력·출처 축의 의미를 먼저 바로잡는다. 행동 분류는 보조 탐색이고, 시간대는 중요도/마감의 대용이 아니다.
3. Hero의 분자·분모·남은 수를 세 번 반복하는 대신 실제 조작 영역을 앞으로 가져온다. 104pt 링을 통일해도 완료 수를100점 척도로 바꾸지 않는다.
4. 기존 하단 완료율을 단순 리디자인 대상으로 보면 안 된다. interval 분모·현재 정의의 과거 소급·주 경계·모집단 차이를 제품 계약에서 해결해야 한다.
5. 자동 성취는 직접 입력의 진행과 별도 출처·기간을 가진다. 전체 규칙 수를 건강 점수나 사용자 과업 수처럼 표현하지 않는다.
6. 구현에 앞서 invalid update가 기존 기록을 지우는 순서를 해결한다. 시각적 만족도가 저장 안전성을 대신할 수 없다.

“마지막 확인09:40”·“조회 중”·“접근 확인 필요”는 현재 Life 진행 DTO가 제공하는 필드가 아니다. 시안의 설명용 상태로는 가능하지만 후속 계획에 새 상태 전달 필요를 명시한다. 고정 시각만 넣고 기존 데이터로 바로 구현 가능하다고 보고하지 않는다. 보고서의 “자동 운동 성취는 Activity에서 확인”은 같은 화면 Life 자동 도전과 기능 위치를 혼동하게 한다. “자동 운동 도전은 위 자동 기록에서” 또는 실제 Activity 목적지를 가진 동작으로 구분한다.

### 동작과 구조 의견

- 시간 수정의 **오늘 총 시간**, 범위 검증 후 적용, 실패 시 기존 값 보존은 적절하다. 0은 오늘 기록 삭제라는 의미이므로 확인 문구나 undo에 그 의미를 전달한다.
- `mutate()`는 전체 화면을 다시 만들고 완료 행을 즉시 접힌 그룹으로 옮긴다. 누른 위치에 다른 항목이 올라오고 키보드 포커스가 사라질 수 있다. 완료 피드백 동안 위치를 유지하거나, 이동 전에 사용자에게 알리고 근처 undo와 안정된 포커스 복원을 제공한다. `returnFocus`는 저장만 하고 복원에 사용하지 않는 현재 구현을 보완한다.
- 맨 아래 toast의 undo는 긴 Life 화면에서 바로 보이지 않을 수 있다. 상단/해당 행 가까운 상태 영역에 두되 콘텐츠를 가리지 않도록 한다. 모든 렌더마다 강제 스크롤하는 방식은 피한다.
- `snooze`는 현재 예시 행을 삭제할 뿐 다가오는 목록에 내일 일정을 추가하지 않는다. 미루기 후 Hero 분모/오늘 목록/다가오는 일정이 같은 상태를 보여야 한다. 되돌리기도 세 영역을 함께 복원해야 한다.
- cycle의 “완료·되돌리기”는 현재 native의 완료 후 재탭 방지 계약과 다르다. 안전한 undo를 신규 동작으로 계획한다면 해당 cycle 로그만 되돌리고 다음 예정일/알림도 복원하는 계약을 명시한다.
- “오늘 시간 기록”·“오늘 완료 기록”은 실제 입력 대신 설명 페이지를 연다. 시안 행동 범위에 이를 명시하거나 버튼을 “기록 방식 보기”로 바꾼다. 완료된 동작처럼 보이는 toast만 제공하지 않는다.
- 개인 습관의 “기록 이력 보기”는 현재 `renderDetail()`에서 모든 오늘 습관을 출력한다. 선택 항목의 이력으로 한정하거나 전체 오늘 기록이라는 제목을 사용한다.
- 횟수0에서 감소 버튼,999에서 증가 버튼은 무효 동작을 “줄임/추가” 성공으로 안내하지 않도록 비활성화하거나 한계를 알려준다. 44px 영역은 확보돼 있으나 disabled 상태도 같은 계약의 일부다.
- 네 목적 필터 자체는 보조 탐색으로 수용 가능하다. 다만 기존12개 아이콘→4개 목적의 정확한 mapping을 문서에 적고, 새 습관 입력이 목적만 저장하는 것처럼 보이지 않게 한다. 신설 분류로 오해되지 않도록 저장 표현과 탐색 표현을 구분한다.
- Compact 비교본은 현재 report/rhythm 순서만 다르고 핵심 정보 위계는 동일하다. 단순 순서 차이를 대안이라고 과장하기보다 기존 위계 보존/행 밀도와 Flow의 실행 우선 구조를 실제로 다르게 보여주거나 비교안을 제거한다.

### 최종 디자인 평가 기준

통합 순서와 입력 유형별44px 컨트롤, 주간 완료일과 하루 목표 분리는 독립안의 핵심을 반영한다. 최종 평가에서는 기능 추가 없이 표현만 바꾸는 항목, 기존 집계 의미를 수정하는 항목, 새 DTO/상태가 필요한 항목을 구분해야 한다. 예시 수치는 자유롭게 정할 수 있지만 **단위·원천·기간·동작 결과의 내부 일관성**은 시안에서도 유지한다.

## 최종 반영 확인 · 2026-10-28

`dune-life-redesign.html`의 보완본과 `docs/design/layout-map/life-redesign-proposal.md`를 read-only 대조했다. 다음 반영을 소스에서 확인했다.

- 걸음 자동 예시는 제거했고 사용자 exercise 오늘 완료/기본 운동횟수/거리로 분리했다. 앱 기록과 HealthKit 연결 기록의 원천, 월–일 기간을 구분했다.
- auto-only에서 수동 오늘/주간/다가오는 구획을 숨겼다.4개 목적의12개 raw value mapping을 명시하고 필터 범위를 오늘 목록으로 한정했다.
- `dailyCounts()`를7일 막대·28일 heatmap·주간 날짜 집계에 공유한다. 주간 로컬 입력은 날짜별 완료 수에 더하지만 오늘 Hero 분모에 넣지 않는다.
- 선택 이력 필터, 미룬 항목의 다가오는 일정 표시, habits/snoozed/weekLogs의 공동 undo,0/999 증감 비활성화를 반영했다.
- 오늘 영역 안에 undo를 배치하고 완료 후 닫힌 details 내부를 피해서 포커스를 복원한다. Compact는 현재 앱 재현본이 아닌 밀도/표현 비교안으로 재정의했다.
- 현재 목표/보관 상태가 과거 완료 개수도 재해석한다는 한계, 운영 조회 metadata 신규 전달 필요, 입력 검증/원자적 저장 선행 과제를 통합 문서에 명시했다.

이 확인 시점의 새로운 P1은 없으며, 다음3개 P2를 parent에게 전달했다. 이후 수정 여부는 해당 경로의 소스 또는 parent 최종 검증 기록으로 확인한다.

| P2 | 재현 가능한 소스 경로 | 필요한 보완 |
|---|---|---|
| 빈 상태에서 추가 후 상태 전환 누락 | `create`는 habits에 추가하지만 `settings.state`를 유지. empty/auto-only의 `today()`는 계속 return, empty Hero도 시작 안내 유지 | 첫 수동 습관 추가 성공 시 정상 상태로 전환. auto-only의 주간 CTA도 존재하는 자동 구획/추가 행동으로 연결 |

남은 범위 제한은 네이티브 Dynamic Type/VoiceOver, 실제 저장 실패/rollback, cycle undo의 다음 예정일·알림 복원, 상세 화면의 실제 데이터 연결이다. 현재 시안은 한국어/로컬 상태의 제안이고 앱 구현 완료 증거가 아니다. 보고서의 날짜 수는 현재 완료가 있는 날을 세므로 “완료한 날”로 명명하면 부분 기록만 있는 날과의 혼동을 줄일 수 있다.

parent가 수행 중인 최종 브라우저 검사와 iPad 행 개선 결과는 이 read-only 확인으로 대체하지 않는다. 이 단계에서는 브라우저 실행·앱 빌드·테스트를 추가로 수행하지 않았다.
