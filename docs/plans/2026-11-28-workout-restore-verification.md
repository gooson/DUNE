# 운동 복원 및 Mac 표시 검증 계획

## 합격 기준

분실 복원, 기존 앱 업그레이드, Mac 열람은 각각 독립적으로 판정한다. 기존 iPad에 남아 있는 기록을 보거나 시뮬레이터에서 JSON을 다시 읽은 결과만으로 Apple 건강 iCloud 복원을 통과시키지 않는다. 합격에 사용한 빌드와 테스트 대상, 실제로 관찰한 값을 남긴다. 위치명, 좌표, 건강 데이터 원본, 계정 식별자는 저장소에 올리지 않는다.

| 검사 | 절차 | 합격 기준 |
|---|---|---|
| 원본 기준 | 연결된 iPad와 Mac에서 운동 ID, 날짜, 운동명, 세트 소유 관계를 읽기 전용으로 비교 | 수정 전후 운동·세트 전체의 필드 및 부모 ID 해시 일치. 신규 운동은 별도 비교 |
| 신규 iPhone 운동 | 앱에서 생성한 합성 근력 운동을 빈 저장소에서 HealthKit 원본으로 다시 읽기 | 운동 ID, 운동명, 세트 순서·중량·횟수가 일치. 재실행·재수신에도 한 벌 |
| 유산소 상세 | 실내 장소만 있는 운동, 경로만 있는 운동, 둘 다 없는 운동 비교 | 원본에 저장된 이름·좌표와 경로만 표시. 임의로 경로 생성 금지 |

| Mac 실제 수신 | 동일 계정, 명시적 근처 전송 활성화, 서로 다른 기기에서 송수신 | 사용자가 지정한 날짜의 유산소·근력 세 행을 원본 ID로 비교. 누락·중복 0건 |
| Mac 실제 지도 | 같은 HealthKit ID의 실내 운동 상세를 양쪽에서 열기 | 같은 운동 ID, 장소명·핀 좌표 일치, 확대 가능한 지도. 위치 누락 화면은 실패 |
| 장애·보안 | 권한 거부, 계정 변경, 키체인 미사용, 중단·재시도, 잘린 패킷·잘못된 버전·중복 ID | 승인되지 않은 전송 및 부분 저장 없음. 다른 계정 캐시 노출 없음 |
| 오프라인 | 수신 후 원본 기기 연결 해제, Mac 앱 재실행 | 이미 수신한 범위가 보존되고 새 데이터 수신 여부와 구분됨 |
| 실제 분실 복원 | 원본 단말을 사용할 수 없는 상태에서 같은 계정의 별도 iPhone에 Apple 건강 데이터 복원. 빈 DUNE 저장소로 앱 실행 | 원본과 날짜·ID·세트·장소 대조. 실물 대상이나 인증이 없으면 미검증 처리. 사용 중인 사용자 기기 초기화 금지 |

## 실행 순서

1. PR의 실제 소스와 기기 목록을 확인한다. 기존 운영 기록과 원본 HealthKit은 임의 변경하지 않는다.
2. 건강 데이터 저장과 비건강 앱 설정을 분리하고 기존 저장소 접근을 점검한다.
3. 같은 운동을 식별할 수 있는 HealthKit UUID를 보존하고, 복원 가능한 정보와 과거 기록에 원래 없었던 정보를 구분한다.
4. Mac 표시를 위해 인증된 기기 간 읽기 전용 복사본을 사용한다. 이 경로를 분실 백업의 근거로 사용하지 않는다.
5. 변경된 경로에 해당하는 자동 검사와 실제 기기 검사를 순차 실행한다. 검증한 커밋을 PR에 포함하고 결과가 없는 항목은 미검증으로 표시한다. 병합은 별도다.

최종 서명본으로 iPad 업데이트를 한 번 더 수행했다. Mac에서는 설치본과 실행본의 DUNE 실행 파일, DUNE.debug.dylib, Assets.car를 서명 제품과 바이트 단위로 대조했다. 세 파일 모두 일치했고 엄격한 서명 검증도 성공했다. 양쪽 설치 전후 운동 400건과 세트 1,949개의 내용 해시는 그대로였다. 별도 장소 테이블은 0건이어서 HealthKit의 운동 장소 유무를 이 테이블로 판정하지 않았다.

전용 iPhone에서 동의 화면 표시·닫기와 설정의 데이터 및 개인정보 화면을 확인하는 UI 테스트 2건이 통과했다. [실제 화면과 증거](../design/phone-design-map/actual/workout-restore-2026-11-28/index.html)에 동의 화면 캡처, 설정 화면의 로컬 XCTest 증거 및 다른 기기의 미촬영 범위를 기록했다.

### 실물 iPad 잠금 해제 후 재검증

| 대상 | 관찰 결과 |
|---|---|
| iPad 후보 | 근처 동기화 스위치 ON을 확인했다. 지정일 운동 3건의 이름을 각각 대조했고, 같은 실내 운동의 상세에서 장소명과 지도 버튼이 표시됐다. 빈 지도·오류 상태 모두 없었다. 실기기 XCTest 두 건 통과. |
| Mac 후보 | 동일한 실내 운동을 열었지만 지도는 빈 상태였고 지정일 운동 3건도 보이지 않았다. |
| 전송 경로 | Mac의 Bonjour 진단에서 iPad 서비스를 발견했다. Mac 후보의 키체인 조회 후 네트워크 브라우저가 시작됐으나 mDNSResponder에서 해당 번들 ID의 로컬 네트워크 정책을 pending으로 기록했다. Mac에 해당 앱의 승인 대화상자가 실제로 표시됐다. 승인 이후 수신 여부는 별도 검사한다. |
| 원본 보존 | 실기기 검사 뒤 iPad와 Mac의 운동 400건·세트 1,949개 필드·부모 연결 해시가 직전 서명본 설치 후 기준값과 모두 같았다. |

Mac에서 앱의 로컬 네트워크 권한이 granted로 바뀐 뒤 지정일의 운동 3건이 표시됐다. 양 기기의 운동·세트 원본 해시는 이전 기준과 일치했다. 실내 운동은 기존 Mac 기록의 HealthKit UUID가 iPad와 일치했으나, 마지막 Mac 상세 조회에서 장소와 지도는 비어 있었다. 과거 이력이 수신되는 동안 이 화면을 반복 탐색하던 자동화를 중지했다. 장소·지도 일치는 아직 미검증이다.

### 동기화 완료 후 실물 장소·지도 대조

실물 iPad와 Apple Silicon Mac의 동일 번들 후보에서 지정한 실내 운동 두 건만 각각 읽었다. 검증용 진입점은 창을 만들거나 권한을 요청하지 않았다. 앱이 사용하는 HealthKit·근처 기록 조회와 로컬 장소 우선순위를 적용하고, 한 번의 검증에만 쓰는 키로 양쪽 결과를 비교했다.

| 항목 | 첫 번째 운동 | 두 번째 운동 |
|---|---|---|
| 날짜별 대상 종목 및 운동 ID | 양쪽 각 1건, 일치 | 양쪽 각 1건, 일치 |
| 표시 장소명 및 핀 좌표 | 모두 일치 | 모두 일치 |
| 지도 표시 조건 및 지도에 전달되는 경로 구간·좌표 | 양쪽 지도 있음, 일치 | 양쪽 지도 있음, 일치 |

이번 대조 범위는 상세 화면의 표시 값이다. 실제 지도 타일의 픽셀이나 확대 조작은 검사하지 않았다. 운동 상세가 열린 뒤 과거 페이지가 도착한 경우에는 해당 운동의 위치를 다시 조회하도록 수정했다. 전용 iPhone 시뮬레이터에서 위치·근처 복원 관련 21개 테스트가 통과했다. 원본 단말 없이 새 실물 iPhone으로 복원하는 시험은 별도로 남아 있다.

### 11월 28일 구버전 전체 저장소와 당시의 분실 복원 검증 범위

V19 로컬 SQLite 파일에 13개 엔터티를 모두 넣었다. 현행 V20에서 두 번 다시 열고 SQLite 내부 키를 제외한 열별 해시, 운동–세트 및 습관–로그의 부모 UUID, 사용자 루틴 항목 ID, 1 MB 이상 첨부 두 개의 실제 바이트 해시를 대조했다. 추가된 장소 엔터티는 비어 있었고 기존 13개 엔터티는 모두 일치했다. 이 시험은 구버전 스키마의 합성 저장소를 사용한다. 실계정 CloudKit에 구버전 앱이 업로드한 13종 전부를 내려받은 시험은 아니다.

| 자료 및 원본 | 기존 기기 업데이트 | 원래 폰을 사용할 수 없을 때 |
|---|---|---|
| 수기·연결 운동, 세트, 메모 | 두 엔터티의 전체 필드와 부모 연결 대조 | 이전 DUNE iCloud 사본에 있던 운동·세트는 읽기 전용 가져오기 지원. Apple 건강에 작성된 새 세트 메타데이터는 기록된 항목만 복원 가능 |
| 운동 장소·경로, 수기 장소 수정 | V20 장소 엔터티와 HealthKit의 핀과 실제 경로를 독립적으로 확인 | 이전 iCloud 장소 레코드와 첨부 읽기, 재실행, 기기 편집과의 충돌을 합성 자료로 검증. 예전 사본에 없는 나중 편집은 별도 원본 필요 |
| 체성분과 수기 메모, 부상과 메모 | 두 엔터티 보존 | Apple 건강의 대응 측정값 외에 DUNE 메모와 부상 이력은 별도 복원 필요 |
| 습관 정의와 완료 로그 | 두 엔터티, 부모 연결, 알림 시각 보존 | 기기에만 있는 로그·수정 사항에 대한 분실 복원 경로 미확인 |
| 자세 평가 및 양면 사진 | 엔터티 전체와 양쪽 첨부 바이트 보존 | 새로운 기기에서 사진 원본 복원 미확인 |
| 사용자 운동·분류·기본값·루틴 | 네 엔터티 및 구조화된 루틴 항목 ID 보존 | 일반 iCloud에는 허용된 즐겨찾기·카탈로그 루틴 필드만 전송. 자유 입력과 실제 운동값은 개별 확인 필요 |
| 건강 미러와 시간별 점수 | 두 엔터티 보존 | 현재 상태 재계산과 당시 점수 보존은 별도 검사 대상 |
| 개인 기록과 리워드 | 별도 UserDefaults 저장. 위 13종 시험에 포함되지 않음 | 운동에서 재계산할 수 있는 항목 외에 과거 점수·배지·이벤트의 동일 복원 미검증 |

실사용 iPhone과 iPad·Mac의 DUNE 저장소도 같은 시점에 읽기 전용으로 대조했다. iPad와 Mac의 운동 및 세트는 같았고, iPhone에는 추가 운동·세트·수기 장소와 공통 운동의 계획 세트 수·노력도 출처, 공통 세트의 계획 반복 수·RPE 출처가 있었다. 습관·자세 등도 기기별 차이가 있었다. 이를 계정 불일치나 운동 삭제로 판정하지 않는다. 오래된 사본에 뒤에 추가된 선택 필드가 없으면 기존 값을 보존하고, 양쪽의 값이 실제로 다르면 가져오기 전체를 롤백한다. 실제 위치·메모·사진·식별자와 검증용 키는 결과물에 포함하지 않았다.

### 파일 백업과 원래 iPhone을 사용할 수 없을 때의 복원

같은 Apple 계정의 각 기기에서 Apple 건강에 접근할 수 있는 범위와 DUNE에서 만든 파일의 범위를 따로 검사한다. DUNE의 iCloud Drive 설정 파일은 테마·앱 아이콘·kg/lb 세 가지 선택만 표현한다. 운동 이름·수치·자유 입력·사진을 넣을 필드가 없다. 운동 등 앱 자료 13종, 자세 사진과 선별된 로컬 설정·리워드를 담은 전체 파일은 별도 복구 키로 암호화한다. 앱이 이 파일을 저장할 수 있는 곳은 백업에서 제외한 기기 내부 폴더와 확인된 이동식 디스크다. 기기 내부에만 있는 파일은 그 기기를 분실하면 사용할 수 없다. 마지막 파일을 만든 뒤의 변경도 그 사본에는 없다. 암호화만으로 개인 건강 정보의 iCloud 저장이 허용된다는 전제를 두지 않았다. | 전체 파일과 손상 | 합성 자료로 13종의 행·운동–세트 및 습관–로그 연결·사진 바이트·선별된 설정과 리워드를 복원했다. 잘못된 키, 손상·교체·잘림, 파일 크기 제한과 32 MB를 넘는 왕복을 검사했다. 재가져오기와 충돌 롤백도 검사했다. |
| 대상 선택 | 설정 파일과 전체 백업의 저장 선택지가 다른지 전용 iPhone에서 검사했다. 일반 파일 제공자는 전체 백업 대상에서 거절된다. 기기 내 전체 파일과 별도 위치 선택을 검사했으며 실물 외장 드라이브 연결·재연결은 미검증이다. |
| 자세 사진 | 합성 JPEG와 PNG의 형식 및 원본 바이트를 검사했다. 실제 자세 상세를 전용 iPhone에 표시해 정면·측면의 원본 저장 버튼을 새로 캡처했다. |
| 분실한 기기 없이 복원 | 원본을 대신한 합성 저장소와 별도의 복원 대상에서 파일 복원을 검증했다. 기기 밖에 전체 파일과 복구 키를 보관한 시점까지가 범위다. 실제 Apple 건강 iCloud와 새 실물 iPhone의 결합 복원은 아직 확인되지 않았다. |

실데이터 건수에 맞춘 합성 회귀도 실행했다. 400건·1,949세트가 있는 대상에 원본 저장소 없이 암호화 파일을 복원해 운동 410건·세트 1,979개와 모든 부모 연결을 대조했다. 누락된 선택 필드만 채웠고 지정 운동 2건의 이름과 장소·핀도 일치했다. 같은 파일을 다시 적용한 결과 추가·갱신 0건이었다. 개인 기록을 이 시험의 입력으로 사용하지 않았다.

최종 파일·복원 회귀 28건, 자세 상세 표시 1건과 설정 화면 UI 검사 1건이 통과했다. 암호화 전 파일 크기 상한은 256 MiB다. 기존 번들 ID의 iPad·Apple Silicon Mac용 후보가 빌드됐고 리소스를 포함한 엄격한 코드 서명 검사가 통과했다. 이 서명본의 실사용 iPhone 전체 복원이나 보유 기기의 자료 일치로 판정하지 않았다.

### Apple 건강과 전체 파일이 서로 다른 순서로 도착하는 경우

검증 기준은 원본 저장소를 제거한 뒤 빈 DUNE 저장소에서 시작해 운동 UUID, 로컬 운동 ID, 세트별 ID·횟수·중량과 부모 운동, 수기 장소, 자세 사진의 SHA-256 및 해당 운동의 리워드 이력을 대조하는 것이다. 이 파일은 생성 시점의 사본이다. 근처 기기나 근처 캐시는 필요하지 않다. 기존 파일 단독 복원과 400건·1,949세트 위에 410건·1,979세트를 병합한 결과는 앞 절의 실행을 재사용한다.

#### 11월 28일 후보에서 파일과 원본 기기가 없을 때

| 남은 자료 | 현재 회수 경로 |
|---|---|
| 이전 DUNE private DB의 운동·세트·운동 장소 | 설정에서 이전 백업 복구를 실행한다. 현재 계정의 기존 zone을 읽어 운동과 세트의 부모 연결, 저장돼 있는 장소 레코드·장소 첨부를 기기로 가져온다. 원격 DB를 수정하지 않는다. 삭제된 레코드나 과거 앱이 쓰지 않은 필드는 복원할 수 없다. |
| Apple 건강에 남은 운동 | 건강 읽기를 허용하면 운동을 조회한다. DUNE가 운동 작성 시 실제로 넣은 세트·장소 메타데이터와 Apple 건강이 제공하는 경로가 대상이다. 같은 운동에 나중에 기록한 DUNE 수기 장소나 별도 자세 사진·리워드는 이 경로에서 생기지 않는다. |
| 이전 private DB에만 있는 자세 사진·평가, 부상·메모, 습관·로그, 사용자 루틴·분류 등 | 11월 28일 후보의 이전 백업 복구는 이 타입을 읽어 복원하지 않았다. 구버전 로컬 저장소가 살아 있는 기기에서는 업데이트한 뒤 전체 파일을 만들 수 있다. 현재의 13종 파일 검증을 원격에만 남은 자료의 회수 증거로 쓰지 않는다. |
| 리워드 및 전체 파일 이후 변경 | 기기에 저장한 리워드는 전체 파일에 포함된 시점까지 복원할 수 있다. 이후 변경·삭제를 전달하는 로그는 이 파일에 없다. 이전 파일에서 복원한 로컬 운동과 Apple 건강의 현재 운동은 각각의 원본 상태를 따른다. |

#### 확인한 복원 결과

| 시나리오 | 관찰값 |
|---|---|
| Apple 건강 → DUNE 파일 | 전용 iPhone 시뮬레이터의 실제 HealthKit에 합성 계단 운동을 저장했다. 운동·세트가 보이는 상태에서 파일을 가져왔다. 운동 목록과 Activity 최근 목록 모두 로컬 운동 1건, 세트 2개(8회·15 kg, 6회·20 kg)였고 부모 운동과 세트 ID가 같았다. |
| DUNE 파일 → Apple 건강 | 파일을 먼저 가져왔을 때 HealthKit에서 해당 UUID는 0건이었다. 같은 운동이 HealthKit에 도착한 뒤 두 목록에 운동이 한 번만 표시됐다. 두 순서 모두 대상 SQLite를 닫고 새 컨테이너로 열어 수기 장소·자세 PNG 해시·리워드 이벤트·개인 기록의 실내 여부를 대조했다. 같은 파일을 다시 가져와도 추가 행은 0건이었다. |
| 열어 둔 상세 | HealthKit 운동 상세가 열려 있는 동안 파일에서 로컬 운동 ID만 있는 장소와 세트를 가져왔다. 같은 창에서 합성 장소명과 세트 값이 표시됐다. [W28 실제 캡처](../design/phone-design-map/actual/workout-restore-2026-11-28/index.html) |
| 파일 A를 만든 뒤 원본에서 수정·추가·삭제하고 파일 B 생성 | 빈 대상에서 A는 수정 전 값과 나중에 삭제된 운동·세트를, B는 수정된 값과 새 운동·세트를 복원했다. A 위에 B를 합치면 같은 필드의 실제 충돌에서 전체를 취소했다. 충돌을 해소한 뒤에는 새 행만 추가했고 B에 없는 로컬 행은 보존했다. 반복 병합은 추가·갱신 0건이었다. |
| 파일 생성 후 Apple 건강에서 같은 운동 삭제 | HealthKit에서 시험 운동을 삭제하고 새 DUNE 저장소로 이전 파일을 가져왔다. 건강 조회는 0건, 앱에는 파일 당시의 로컬 운동 1건과 세트 2개·수기 장소가 남았다. 앱 저장소를 재개방해 다시 가져와도 HealthKit에 운동이 재생성되지 않았다. |

시뮬레이터의 시험 운동은 이번 실행이 만든 UUID와 DUNE 출처를 확인해 정리했다. 두 순서 시험은 시스템 HealthKit 저장·조회를 사용했다. Apple 건강의 실제 iCloud 서버 다운로드, 실물 외장 드라이브에서 파일 열기, 설정 파일의 iCloud Drive 서버 수신은 미검증이다. 앞선 계정 오류 4355 이후 같은 Drive 시험을 반복하지 않았다.

### 11월 29일 실물 iPad에서 원본 없이 복원

전용 iPhone 시뮬레이터의 `HealthKitAndFileArrivalTests/testExportSyntheticReplacementDeviceFixture`에서 암호화한 합성 파일을 만들었다. 원본 저장소를 제거한 뒤 백업 파일과 시험용 복구 키·기대값만 iPad 검증 컨테이너에 전달했다. iPad에서는 후보 앱과 동일한 Mach-O UUID의 DUNE 라이브러리를 별도 번들에 서명해 실제 파일 가져오기 경로를 실행했다. 검증기는 HealthKit·iCloud·앱 그룹 권한이 없었다.

| 실물 iPad 검사 | 관찰값 |
|---|---|
| 빈 SQLite 저장소에 첫 복원 | 운동 1건, 세트 2개, 수기 장소 핀 1개, 자세 사진 1개가 추가됐다. 운동·세트 ID, 부모 연결, 횟수와 중량, 메모, 장소, 사진 원본 SHA-256, 개인 최고 기록과 리워드 이벤트 2건이 원본 기대값과 일치했다. |
| 종료 후 새 프로세스에서 재개방 | 파일을 다시 가져오기 전에 같은 값을 읽었다. 같은 파일을 재복원한 뒤 추가 행은 0건, 리워드는 2건이었다. 목록에 같은 UUID의 합성 건강 운동을 전달했을 때 운동은 한 번만 표시됐다. |
| 화면과 개인 자료 | 두 실행 모두 화면 활성화 없이 종료 코드 0이었다. 검증 번들을 삭제한 뒤 기기에서 사라진 것을 확인했다. 기존 DUNE 프로세스는 시험 전후 동일했다. 개인 앱 저장소는 읽거나 쓰지 않았다. |

이 결과는 원본 폰이 없어도 보관해 둔 파일과 복구 키로 iPad에서 DUNE 자료를 복원할 수 있음을 확인한다. 실물 iPad에 파일을 전달한 경로는 개발자 파일 전송 서비스였다. 실물 iPad에서 Apple 건강이나 iCloud 서버로부터 수신했다고 판정하지 않는다.

### 11월 29일 구버전 CloudKit 스키마와 보관된 증거

로컬 V19에는 모델이 13종, 장소가 추가된 V20에는 14종이다. 전체 파일의 13종은 **V20에서 건강 미러 캐시를 제외한 13종**이다. 배포 미리보기의 11종은 **그 배포에서 생성할 타입의 차이**다. 11종 목록에 없는 세 타입의 운영 스키마 상태와 계정별 기록 수는 그 화면으로 확인할 수 없다.

| `CD_HealthSnapshotMirrorRecord` | 생성 | `id`, `fetchedAt`, `syncedAt`, `sourceDevice`, `payloadVersion`, `payloadJSON` |

운영 운동·세트 요약에서 관측된 `CD_exerciseRecord`는 부모 레코드 이름 문자열이었다. `CD_primaryMusclesRaw`·`CD_secondaryMusclesRaw`는 Data였다. 실제 운동에 `CD_plannedSetCount`, `CD_effortSourceRaw`, 세트에 `CD_plannedReps`, `CD_rpeSourceRaw`가 항상 있다고 가정할 수 없다. 자세 사진은 `frontImageData`·`sideImageData`의 원본 바이트를 별도로 확인해야 한다. 타입 존재, 합성 CKAsset 디코딩, 운영 자산 수신과 바이트 일치는 각각 다른 검증이다.

**스냅샷과 기본 설정.** 건강 미러는 직렬화한 당시 상태다. 현행 `HealthSnapshotMirrorStore`는 최대 240개를 유지하고 미러 전용 `health-snapshot-mirror.store`의 CloudKit은 꺼져 있다. 운동 세트 원본·경로 전체·자세 사진을 미러에서 복원할 수 없다. 시간별 점수는 별도 엔터티이며 실제 보관된 날짜와 점수만 복원할 수 있다. 개인 최고 기록과 리워드 이벤트는 활동별 UserDefaults와 단일 리워드 상태에 있다. 이 저장소는 최근 이벤트 최대 500개와 처리 서명 최대 2,000개를 유지한다. 기록이 잘리기 전의 과거 이력을 재구성하는 원장이 아니다. 체크된 앱 설정, DUNE 전체 파일과 Apple 건강의 포함 범위는 위 파일 검증표를 따른다. 전체 파일 v2는 직렬화 원본 256 MiB까지 허용하며 한도를 초과하면 전체 저장을 실패 처리한다.

**운영 확인 방법.** 운영 스키마는 Console에서 Production의 Record Types 및 개별 필드 또는 읽기 전용 스키마 내보내기로 확인한다. 계정의 실제 기록 수는 해당 계정의 기존 private zone을 변경 토큰 없이 처음부터 마지막 페이지까지 읽고, 속성 값이 필요 없는 조사에는 `desiredKeys: []`를 지정한다. 페이지별 성공만 집계하고 변경과 삭제를 ID 기준으로 반영한다. 한 항목이라도 읽기에 실패했거나 계정이 바뀌면 전체 집계를 미확인으로 남긴다. 외부 결과에는 타입별 개수만 남긴다. 한 계정·한 존의 0건으로 다른 계정이나 운영 스키마 전체에 자료가 없다고 결론내릴 수 없다.

#### 운영 계정의 현재 private zone 확인

11월 29일 HAL에서 Production 서명을 확인한 읽기 전용 도구로 Core Data private zone의 첫 변경 토큰부터 마지막 페이지까지 읽었다. `desiredKeys: []`로 필드와 첨부를 요청하지 않았고 삭제 이벤트를 반영했다. 조회 시작·종료 시 같은 계정임을 확인했다. 이 표는 현재 남아 있는 행을 나타낸다. 삭제 이력이나 다른 사용자의 보관 상태는 판정하지 않는다.

| 현재 남은 자료 | 읽기 결과 |
|---|---:|
| 운동 | 400건 |
| 세트 | 1,949건 |
| 건강 미러 스냅샷 | 22건 |
| 시간별 점수 | 6건 |
| 운동 장소, 체성분, 사용자 운동, 루틴, 부상, 습관 정의·로그, 분류, 운동별 기본값, 자세 평가·사진 레코드 | 각 0건 |

별도 장소 레코드가 없더라도 Apple 건강의 운동 메타데이터나 다른 경로로 화면에 보이는 장소가 있을 수 있다. 리워드 이력은 구버전 private zone에 대응하는 모델이 없었고, 자세 사진은 자세 평가 행의 첨부 필드였다. 서버에 이미 삭제된 사진이나 전송한 적이 없는 사진을 재구성하는 경로는 없다.

#### 구버전 private zone에서 DUNE 설정으로 복원

후보 앱은 이전 private zone만 읽고, 14개 모델을 같은 로컬 SwiftData 트랜잭션에서 복원한다. 예전 계정에서 생성하지 않은 존은 비어 있는 백업으로 처리한다. 습관 로그와 세트의 부모는 zone을 포함한 CloudKit 레코드 ID로 찾고, 로컬 모델은 자체 논리 ID로 대조한다. 이 시점 후보는 시간별 점수를 원본 시간대로 식별했다. 아래 운영 4종 대조에서 같은 시간대의 별도 행을 확인했다. 같은 데이터의 재수신은 기존 행을 보존한다. 백업에 빠진 선택 필드 때문에 기기에 남은 값을 지우지 않는다.

| 시나리오 | 검증 결과 |
|---|---|
| 원본과 전체 파일 없이 빈 기기 저장소에 이전 | 실제 설정의 복원 동작에 순서를 뒤섞은 14종 합성 CKRecord를 전달했다. iPhone 시뮬레이터에서 운동·세트·장소 각 1건과 기타 11건을 복원했다. |
| SwiftData 파일을 다시 열고 같은 자료 재수신 | 운동·세트와 습관·로그의 ID 및 부모 관계, 분류·사용자 운동·루틴의 항목, 부상, 체성분, 점수와 미러, 자세 사진 원본 SHA-256을 대조했다. 두 번째 복원에서 추가된 행은 0건이었다. 루틴·근육 배열은 SwiftData가 직접 기록한 합성 SQLite의 바이트를 사용했다. |
| 잘못된 값과 끊긴 연결 | 체중 충돌, 사라진 부모 또는 다른 zone의 부모 참조, 읽을 수 없는 첨부를 주입했다. 앞에서 처리한 행도 저장되지 않았고 기존 사진·부모·체중은 보존됐다. |
| 회수 가능 범위 | 이번 계정에 있는 타입과 합성 대상으로 검증한 타입을 위 집계로 구분한다. 사용자 루틴·습관·자세·부상은 그 계정의 해당 행과 첨부가 있어야 복원된다. 앱 리워드의 UserDefaults 이력, 삭제된 서버 데이터, HealthKit의 실제 운동 경로는 이 private zone의 복원 대상 밖이다. |

전용 iPad 시뮬레이터에서도 빈 저장소·재개방 검사가 통과했다. 앞·옆 자세 사진 두 장을 별도 자산으로 받아 원본 해시와 자세 지표·관절 좌표, 부상 양상·날짜·메모를 대조했다. 같은 사진을 인라인으로 다시 받아도 추가 행은 0건이었다. 한쪽 사진 변경, 중복 표현, 32 MiB를 초과하는 첨부는 거부됐고 같은 시도에서 앞서 처리한 부상 행도 남지 않았다. 현재 사진당 32 MiB, 변환 가능한 배열·텍스트 자산당 4 MiB가 입력 한도다. 알려지지 않은 형식을 복구한 것으로 간주하지 않는다.

[설정의 iPhone·iPad 실제 캡처](../design/phone-design-map/actual/workout-restore-2026-11-28/index.html)에서 운동·세트·장소·기타 기록 수를 확인했다. 동일 번들 후보 빌드와 리소스를 포함한 엄격한 서명 검사가 통과했다. 추가 실물 iPad 검사에서는 iPadOS가 기기 잠금으로 새 검증 프로세스 실행을 거부했다. 따라서 이 구버전 CloudKit 경로의 실물 iPad 실행은 미검증이다. 앞 절의 실물 iPad **파일 복원** 성공은 그대로 유효하다. Apple 건강 및 iCloud Drive의 서버 수신은 이 시험에 포함하지 않았다.

### 운영 private zone에 남은 네 종류의 복원 대조

운영 타입 집계 다음에 `58552ec0`의 복원 코드를 사용해 실제 행을 빈 로컬 저장소로 가져왔다. 처음에는 시간별 점수에서 중복 판정이 발생해 트랜잭션이 중단됐다. 여섯 행은 네 시간대에 걸쳐 있었다. 같은 시간대의 각 쌍은 생성 시각이 다르고 일부 지표가 한 행에만 있었다. 실제 기록 시각, 측정값, 계정과 레코드 ID, 미러 JSON을 로그나 이 문서에 남기지 않았다.

검증기는 Production CloudKit 서명을 사용했다. 읽기 권한으로 이전 private zone을 끝까지 열거하고 해당 네 타입만 조회했다. 두 프로세스 사이의 계정과 서버 레코드 버전은 일회용 키로 비교했다. Mac 대상에는 후보의 SwiftData 모델·스키마·미러 디코더·복원 코드를 그대로 빌드했다. 로컬 저장소의 CloudKit 구성을 끄고, 개인 값을 읽기 전에 macOS 백업 제외 상태를 확인했다. 체크포인트, SQLite 부속 파일, 임시 수신 파일은 같은 격리 폴더에서 처리했다.

수정본은 동일한 시간대에 작성된 점수 행을 생성 시각까지 대조한다. 여섯 원본 행을 각각 유지하고 서로 다른 행의 빈 지표를 합치지 않는다. 같은 행의 필드 충돌이나 어느 행에 해당하는지 식별할 수 없는 변경은 로컬 저장 전에 중단한다. 시간대당 한 행인 기존 v1 전체 파일의 식별자를 계속 읽고 쓴다.

| 운영 자료 | 빈 저장소에 추가 | 별도 프로세스에서 재개방·재복원 | 비공개 대조 |
|---|---:|---:|---|
| 운동 | 400 | 추가 0 | 운동 ID, 원본 시각, 선택값·수치·문자열·배열·바이너리, 세트 역관계 모두 일치 |
| 세트 | 1,949 | 추가 0 | 세트 ID, 부모 운동 ID, 순번·완료·횟수·무게 등 필드 모두 일치 |
| 건강 미러 | 22 | 추가 0 | ID, 수집·동기화 시각, 출처, 버전, JSON 원문 UTF-8 바이트 모두 일치. 앱 디코더로 22건 모두 읽음 |
| 시간별 점수 | 6 | 추가 0 | 각 행의 시간대·생성 시각, 일곱 점수·측정 필드가 빈 값까지 모두 일치 |
| **합계** | **2,377** | **추가 0** | 재개방 직후와 재복원 직후 두 번 모두 원본과 대조 통과 |

두 번째 프로세스 종료 후 임시 SQLite·WAL·부속 파일 및 일회용 비교 표시가 든 디렉터리를 삭제하고 부재를 확인했다. 운영 DB는 읽기만 했다. 실제 작업을 실행한 대상은 Mac의 격리된 로컬 저장소였다. 잠긴 실물 iPad는 다시 조작하지 않았다.

전용 iPad 시뮬레이터에서 관련 회귀 검사 10개가 통과했다. 합성 6행의 역순·부분 복구, 빈 지표 유지, 암호화 전체 파일 왕복, v1 날짜 단독 식별자, 수정된 생성 시각·모호한 밀리초 대응·실제 값 충돌에서 롤백을 검사했다. 오래된 기기에서 이미 백업 파일을 만든 경우도 포함한다.

**Apple 건강 iCloud 수신은 별도 미검증이다.** 앞서 실물 iPad로 전달한 파일 복원, 시뮬레이터의 HealthKit 로컬 저장·조회, DUNE private zone에서 받은 건강 미러는 각각 다른 경로다. 서버 수신을 입증하려면 동일한 Apple 건강 iCloud 계정의 수신 기기에서 고유 시험 운동이 처음에는 없고, 발신 기기가 올린 뒤 DUNE 파일·근처 전송을 사용하기 전에 수신 기기의 HealthKit에서 같은 UUID·시각·출처와 저장된 메타데이터를 직접 읽어야 한다. 발신 기기 없이 복원되는지 판정하려면 서버 업로드 후 수신 전 원본을 분리한다. 수신 기기는 iPad도 사용할 수 있다.

### 실물 iPad에서 DUNE iCloud 설정을 바꾼 뒤 Apple 건강 운동 표시 확인

사용자가 같은 Apple 계정으로 확인한 실물 iPad에서 iPhone을 조작하지 않고 검증했다. 동일 번들 ID의 서명 빌드를 전면 활성화 없이 실행해 iPad의 HealthKit에서 30일간의 운동을 조회하고, 읽기 전용으로 연 DUNE 기록과 함께 활동 화면의 실제 목록 생성 함수에 전달했다. 각 HealthKit 운동의 UUID로 건강 행과 연결된 수동 입력 행을 모두 세었다. 작성 앱을 제한하지 않았으며 삭제 처리된 표본은 없었다.

| iPad의 DUNE iCloud 설정 | 원본 운동마다 목록에 정확히 한 행 | 누락 | 중복 |
|---|---|---:|---:|
| 끔 | 전체 일치 | 0 | 0 |
| 켬 | 전체 일치 | 0 | 0 |
| 다시 끔 | 전체 일치 | 0 | 0 |
| 끔 상태에서 프로세스 재실행 | 전체 일치 | 0 | 0 |

설정 화면과 같은 저장 함수를 사용했고, 단계마다 기기 설정값과 iCloud 키-값 저장소의 값을 다시 읽었다. 네 단계의 운동 식별자와 각 행의 개수가 일치했다. 개인 기록에는 쓰지 않았다. 이 시험은 iPad가 이미 보유한 건강 기록의 목록 표시를 검증했다. 새 기기에서 Apple 건강 서버로부터 처음 내려받는 과정은 별도 검증이 필요하다.
