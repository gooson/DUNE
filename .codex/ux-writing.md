# DUNE UX Writing · Codex 보완 규칙

확인일: **2026-10-28**. 사용자 대면 제목·본문·버튼·알림·오류·빈 상태·접근성 레이블을 작성하거나 검토할 때 적용한다. `.claude/skills/copy-voice/SKILL.md`의 차분하고 존중하는 목소리는 유지하고, 아래 항목은 Codex 실행에서 해당 스킬의 제한을 보완·대체한다. 앱 전체 문구를 자동으로 수정할 권한을 뜻하지 않는다.

## 근거와 적용 범위

공식 문서에서 확인한 원칙을 DUNE 상황에 맞게 아래 규칙으로 구체화했다. 확인일은 문서의 발행일이나 개정일이 아니다. 모든 내용을 ‘2026년 신규 지침’으로 부르지 않는다.

| 근거 | 확인한 내용 | DUNE 적용 |
|---|---|---|
| [Apple HIG · Writing](https://developer.apple.com/design/human-interface-guidelines/writing) | 상황에 맞는 톤, 명료한 행동명, 용어 일관성, 오류와 빈 상태의 안내. 페이지 변경 이력에 2025-12-16 개정이 표시돼 있다. | 맥락과 실제 동작을 먼저 확인하고 표현을 정한다. |

## 작성·검토 기준

1. **상태와 다음 행동부터 확인한다.** 누구에게, 어떤 시점에, 어떤 근거로 보여주고 버튼을 누르면 무엇이 일어나는지 파악한다. 저장되지 않았는데 ‘저장됐어요’, 위치 이동을 감지했을 뿐인데 ‘운동이 끝났어요’라고 쓰지 않는다.
2. **제목은 핵심 상황이나 결정, 본문은 추가 정보다.** 같은 질문·결론을 다른 표현으로 다시 쓰지 않는다. 본문을 지워도 판단에 필요한 정보가 모두 남으면 본문을 생략할 수 있다. 이유·영향·복구 방법 중 필요한 내용만 보탠다. [근거: Apple Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts), [WWDC25](https://developer.apple.com/videos/play/wwdc2025/404/).
3. **단어가 아니라 의미의 반복을 찾는다.** ‘마칠까요?’와 ‘끝났나요?’처럼 단어가 달라도 같은 결정을 두 번 묻는지 확인한다. 다만 독립적으로 읽히는 버튼·접근성 레이블에서 대상 명칭을 반복하는 것은 명확성을 위해 허용한다.
4. **버튼만 보고 결과를 예상할 수 있게 쓴다.** 구체적인 행동에는 ‘운동 종료’, ‘다시 시도’, ‘설정 열기’처럼 필요한 대상을 포함한다. ‘확인’은 단순 정보 수용에 사용한다. 실제 다음 화면이 입력 단계라면 최종 처리가 끝나는 것처럼 약속하지 않는다. [근거: Apple Writing](https://developer.apple.com/design/human-interface-guidelines/writing), [GOV.UK Button](https://design-system.service.gov.uk/components/button/), [토스](https://toss.tech/article/21022).
5. **짧게 쓰되 결정에 필요한 정보는 남긴다.** 한 문장에는 한 가지 내용을 담고 핵심을 먼저 쓴다. ‘쉽게’, ‘빠르게’, ‘성공적으로’, ‘지금 바로’는 실제 구분이나 검증된 정보가 없으면 뺀다. 감사·사과·권유를 의무적으로 붙이지 않는다. [근거: WWDC25](https://developer.apple.com/videos/play/wwdc2025/404/), [GOV.UK Writing](https://www.gov.uk/service-manual/design/writing-for-user-interfaces).
6. **차분한 목소리 안에서 상황에 맞게 말한다.** DUNE 한국어 설명·안내는 해요체를 기본으로 하고 버튼·지표는 짧은 행동명·명사형을 쓴다. 오류·권한·손실 안내에는 농담·과장·사용자 탓을 넣지 않는다. 심각한 결과를 친근한 표현으로 흐리지 않는다. 이 말투는 DUNE의 제품 선택이며 모든 언어의 공통 문법은 아니다. [근거: Apple Writing](https://developer.apple.com/design/human-interface-guidelines/writing), [Apple Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts).
7. **관측·추정·미수신을 구분한다.** 건강 점수나 센서 신호가 뒷받침하지 않는 상태를 확정하지 않는다. 기록을 아직 받지 못한 상태를 0이나 활동 없음으로 바꾸지 않는다. 같은 동작·지표는 동일한 용어를 쓴다. [Apple Writing](https://developer.apple.com/design/human-interface-guidelines/writing)의 명료성·일관성을 적용한 DUNE 규칙이다.
8. **기기와 언어에서 읽히는지 확인한다.** Watch는 제목과 행동을 빠르게 파악할 수 있도록 먼저 다듬는다. 단어 수·글자 수만 맞추려고 의미를 빼거나 아이콘으로 대체하지 않는다. 색·위치만 가리키는 안내를 피한다. 번역·큰 글씨·VoiceOver 맥락을 고려하며 실제 화면 검증은 기존 프로젝트 게이트를 따른다. [근거: Apple Writing](https://developer.apple.com/design/human-interface-guidelines/writing), [GOV.UK Writing](https://www.gov.uk/service-manual/design/writing-for-user-interfaces).

## 상태별 문구 패턴

아래는 제품 패턴이며 항상 두 문장이나 본문을 요구하는 템플릿은 아니다. 예시는 해당 동작·저장 상태가 실제로 구현된 경우에만 쓴다.

| 상황 | 전달할 정보 | DUNE 예시 |
|---|---|---|
| 종료 확인 | 결정 + 필요한 감지 이유 + 분명한 선택 | 제목 ‘계단 운동을 마칠까요?’ / 본문 ‘이동이 감지됐어요.’ / ‘운동 종료’·‘계속 운동’ |
| 작업 오류 | 안 된 작업 + 실제 가능한 복구 행동. 원인은 확인된 경우만 포함 | ‘운동 기록을 저장하지 못했어요.’ / ‘다시 시도’ |
| 입력 오류 | 수정할 항목·조건을 해당 입력 가까이 안내 | ‘운동 시간을 입력해 주세요.’ |
| 첫 사용·빈 기록 | 아직 없는 대상 + 가능한 시작 경로 | ‘아직 운동 기록이 없어요.’ / ‘운동 시작’ |
| 조회 중·기록 미수신 | 아직 확인 중인 상태를 실제 빈 기록과 구분 | ‘운동 기록을 불러오는 중이에요.’ |
| 권한 요청 | 필요한 기능과 접근 이유 | ‘기구에서 내려와 이동하면 운동을 마쳤는지 묻기 위해 위치를 사용해요.’ |
| 되돌릴 수 없는 손실 | 영향을 받는 대상·결과를 숨기지 않음 | ‘저장하지 않은 운동 기록이 삭제돼요.’ — 실제 삭제되는 경우만 사용 |

## 동작 용어

| 표현 | 의미와 사용 조건 |
|---|---|
| 운동 종료 | 현재 운동 기록을 끝내는 명시적인 행동 |
| 계속 운동 | 종료 제안을 닫고 현재 운동 기록을 유지 |
| 재개 | 일시정지한 운동을 다시 진행 |
| 저장 | 데이터를 저장하는 행동. 저장 요청·저장 중·저장 완료를 혼동하지 않는다. |
| 완료 | 현재 입력·설정 흐름을 마침. 추가 저장 여부는 구현에 맞춰 판단한다. |
| 다시 시도 | 실패한 작업을 다시 실행 |
| 닫기 / 취소 | 표시만 닫는지, 진행 중인 입력·행동을 중단하는지 구분 |

기존 화면·브랜드·국제 운동명·내비게이션 제목의 명명 및 번역 예외는 프로젝트의 기존 규칙을 따른다. 이 목록을 근거로 모든 화면에 일괄 치환하지 않는다.

## 기존 copy-voice 규칙과의 차이

| 기존 제한 | Codex 적용 기준 |
|---|---|
| Watch 버튼은 1단어·카드/레이블은 최대 2단어 | 짧고 명확한 행동·대상 조합을 우선한다. ‘운동 종료’·‘계속 운동’을 단어 수 때문에 줄이지 않는다. Apple Alerts의 1–2단어 권장은 간결성 목표이며 모든 언어·컴포넌트의 강제 상한이 아니다. |
| ‘에러/오류/실패’를 항상 ‘데이터를 불러올 수 없습니다’로 대체 | 실제 실패한 작업을 명시한다. 저장 오류를 불러오기 오류로 바꾸거나 원인을 추측하지 않는다. |
| 부정적인 단어 금지 | 비난·과장·공포 유도는 피하되 실제 손실·작업 실패·필요한 주의는 명확히 전달한다. |
| 모든 오류에 안내 문장을 덧붙임 | 사용자가 실행할 수 있는 복구 행동만 제공한다. 이미 명확한 버튼을 본문으로 다시 설명하지 않는다. |
| ko/ja의 고정 번역 길이 비율·축소값으로 해결 | 검증되지 않은 비율을 규칙으로 쓰지 않는다. 실제 번역과 대상 기기·큰 글씨에서 판단한다. |
| 모든 숫자에 단일 helper·고정 자릿수 | 기존 locale 대응 포매터와 지표의 정밀도를 따른다. 이 문구 규칙이 숫자·단위 구현을 일괄 변경하지 않는다. |

## 적용과 유지

- 문구 변경은 같은 의사결정의 제목·본문·버튼·접근성 레이블을 함께 검토한다. 겹치는 단어 수만으로 판정하지 않는다.
- 소리 내어 읽고, 본문을 지웠을 때 잃는 정보와 버튼 선택 결과를 확인한다. 새 정보가 없는 문장과 모호한 행동명은 수정한다.
- en/ko/ja 카탈로그, 시스템 권한 문구, 포맷 정리와 실제 화면 디자인맵은 기존 localization·캡처 규칙을 따른다. 번역 문장은 각 언어에서 자연스럽게 다듬는다.
- 규칙 문서만 바뀌면 링크·adapter parity·diff를 검증한다. 이를 이유로 앱 전체 빌드·UI 테스트를 실행하지 않는다.
- 규칙을 실제 작업에 적용하다 모호한 용어를 발견하면 범위·의미를 먼저 정리해 용어 표를 보완한다. 공식 지침 개정이나 새 기기/언어 적용 시 관련 출처를 다시 확인하고 확인일과 변경 이유를 기록한다.
